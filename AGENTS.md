## Workflow — TL + sous-agents dev v2.3 (2026-11-20)

Version complète : **`docs/workflow.md`** (copie du workflow commun `~/.claude/workflows/duo-tl-dev.md`), à lire en entier en début de rôle et avant une étape inhabituelle (batch empilé, revue). L'essentiel :

- **Rôles** : l'utilisateur donne les go, teste et valide (« <n> ok » = merge de cette PR) ; le **TL** est la **seule session** du projet : il cadre, rédige les tickets, **lance un sous-agent dev par carte** (gabarit `docs/sous-agent-dev.md`), revoit, donne les plans de test, merge, tient Trello et le journal. Le **sous-agent dev** traite une carte cadrée + ticket + go, ouvre une PR draft tout de suite, la passe en ready et rend un rapport final au TL. Le TL ne code pas les cartes lui-même (correctif trivial ou mécanique toléré).
- **Garde-fous** : diff relu et checks relancés par le TL, au moins une mesure visuelle par le TL pour toute carte d'interface, revue indépendante pour une carte `[L]` ou sensible ; questions ouvertes des rapports tranchées ou remontées, jamais perdues.
- **Boucle de relecture** : pour une carte `[M]`, `[L]` ou sensible (données des questions, stockage local, examen), dès le ready du sous-agent dev et avant la revue du TL, un sous-agent relecteur (`docs/relecteur.md`) relit le diff et le code qui lit ce qui change, avec le catalogue `docs/catalogue-bloquants.md`. Corrections, nouvelle relecture, jusqu'à « prête à fusionner » ; au-delà de 3 tours ou sur un point métier, remontée à l'utilisateur. Une carte `[S]` et les PR de doc gardent la seule revue du TL.
- **Carte** : cadrage validé dans le chat avant le board, taille `[S]` / `[M]` / `[L]`, ticket dev dans la carte, Done **et** entrée du journal dans la même respiration.
- **Batch** : un seul go ; tickets revérifiés sur le code avant le go ; un sous-agent à la fois ; cartes regroupées dans une liste « Batch — … », archivée une fois toutes les cartes traitées ; PR testées ensemble marquées comme un même **lot** au tableau de bord.
- **Revue** : une seule, au ready ; tests, lint, build lus en entier ; contrôle visuel mobile mesuré ; commentaire de PR ; plan de test **au tableau de bord seulement**, résumé court à l'utilisateur. PR sans rien de testable avant le merge : « rien à tester de ton côté, donne ton go », et le TL vérifie lui-même en production.
- **Maquettes** (décision de l'utilisateur, 2026-11-23) : toute l'appli est maquettée dans un Artifact privé, https://claude.ai/artifact/GaE1VRaaqK5fqND5BsBiqx (une page « Application actuelle », une page par carte d'interface). Tout ajout ou changement d'interface est d'abord répercuté dans les maquettes et **validé par l'utilisateur avant le go dev** ; le sous-agent dev reçoit les maquettes validées comme référence ; après le merge, le TL reporte le changement sur la page « Application actuelle ».
- **impeccable** sur toutes les cartes d'interface (décision du 2026-11-20) : `shape` au cadrage, chargé par le sous-agent dev avant d'éditer l'UI, `critique` / `audit` en relecture et en revue. `PRODUCT.md` (vérité produit) existe depuis le 2026-11-23. **Direction de design retenue par l'utilisateur (2026-11-23) : « la carte du parcours »** (page « La carte du parcours · toutes les pages » du canevas de maquettes) ; design system léger : thème shadcn personnalisé + quelques composants propres. **`DESIGN.md` existe depuis le 2026-11-24** (racine du dépôt, écrit avec impeccable `document` sur la v1.6.1, sidecar `.impeccable/design.json`) : jetons, composants et règles visuelles de l'appli, à lire avant toute carte d'interface ; les maquettes validées d'une carte priment sur lui pour ce qu'elles changent, et `DESIGN.md` est mis à jour quand une carte fait évoluer le design system.
- **Git** : jamais de push sur `main` ; PR automatique ; défaut trouvé en test corrigé dans la même PR ; PR de doc (journal, AGENTS.md, gabarits) mergée par le TL dès que ses checks passent, sans demander le go (décision de l'utilisateur, 2026-11-26) ; version incrémentée par carte ; chacun ne supprime que ses branches ; jamais affirmer l'état d'une PR sans `gh pr view`.
- **Isolation** : sous-agents dev dans le worktree dev (port 5211), un à la fois, worktree laissé en HEAD détaché ; TL dans le worktree de revue (5212) ; relecteur sur une copie jetable (`vite preview` sur 5213) ; arrêt des serveurs par PID exact uniquement.
- **Modèles des sous-agents** (décision de l'utilisateur, 2026-11-26) : ceux qui écrivent (sous-agent dev, rédacteur de contenu, corrections) sur **Sonnet** (`model: "sonnet"`) ; ceux qui vérifient (vérificateur de contenu, relecteur) sur **Opus** (`model: "opus"`) ; en cas de doute ou de désaccord entre rédacteur et vérificateur, un **arbitre** sur **Fable** (`model: "fable"`) relit les seules questions ou points en cause, sources à l'appui (`docs/verificateur-contenu.md`). Un doute sans source officielle reste tranché par l'utilisateur.
- **Économie** : messages synthétiques, une session TL par batch ou journée ; le TL propose `/save` lui-même aux états stables (voir `docs/workflow.md`, section 12).

## Produit

**Futur Citoyen** (nom retenu le 2026-11-24, ex-« Test Civique » ; domaine https://futurcitoyen.fr depuis le 2026-11-24, l'ancienne adresse test-civique.netlify.app y redirige en 301 ; le dépôt, le board et les aperçus Netlify gardent « test-civique ») : application d'entraînement à l'examen civique, pour la carte de séjour pluriannuelle, la carte de résident (depuis la v1.14.0) et la naturalisation (depuis la v1.21.0) : choix sur l'écran du titre visé, `/titre`, qui s'ouvre sur le titre déjà choisi. Site indépendant, non officiel : mention en pied de l'accueil avec lien vers formation-civique.interieur.gouv.fr. Production : https://futurcitoyen.fr

Règles officielles (arrêté du 10 octobre 2025, art. 1 à 4) : 40 questions, 4 choix, une seule bonne réponse, 45 min au maximum, 1 point par bonne réponse et 0 sinon, réussite à 80 % (32/40). Rappelées sur la page « Comment se passe l'examen » (`/regles`, lien depuis l'accueil).

- **Examen blanc** : un seul examen, **conforme à la répartition officielle** (depuis la v1.9.0) : 40 questions tirées selon `EXAM_BLUEPRINT` de `src/lib/exam.ts` (nombre exact de questions par thème et sous-thème, dont 12 mises en situation, 6 en Principes et valeurs et 6 en Droits et devoirs ; une case qui manquerait de questions se complète dans son thème, puis dans le reste ; depuis la v1.15.0, les questions du dernier examen terminé du même titre ne sont reprises qu'en dernier recours, jamais au détriment de la répartition ni des groupes : `previousExamQuestionIds` et `buildExam(pool, { avoid })`, une reprise ne change pas, un examen ancien sans `answers` n'évite rien), **chrono global de 45 minutes** (pas de chrono par question ; **arrêté pendant l'affichage de la correction**, il repart à la question suivante, depuis la v1.24.0 ; un examen en cours sauvegardé garde son temps restant ; sous 5 minutes, barre du temps en corail et pastille « Moins de 5 minutes », annonce vocale faite aussi à la reprise). L'étape 2 de l'accueil et « M'entraîner maintenant » sur `/regles` reprennent directement l'examen en cours du titre choisi s'il y en a un (jamais effacé sans prévenir), sinon mènent à la page **« Examen blanc »** (`/examen-blanc`, depuis la v1.19.0 : titre visé, « Comme le jour J » en 4 repères, « Ce qui change ici », bouton « Commencer l'examen blanc » qui tire un nouvel examen, lien vers `/regles`) ; arrivé sur cette page par l'adresse avec un examen en cours, le bouton principal devient « Reprendre l'examen (question n sur 40) » et « Commencer un nouvel examen » demande confirmation (« L'examen en cours sera abandonné ») ; seul « Nouvel examen blanc » de l'écran de résultat tire directement un nouvel examen, sans cette page. Chaque question : choix → « Valider » → correction avec explication → « Question suivante ». À l'expiration du chrono, les questions restantes comptent comme « sans réponse ». Le résultat affiche « Réussi » ou « Pas encore réussi » (seuil `passThreshold` = 80 % du total, arrondi au supérieur, dans `src/lib/exam.ts`), à l'écran de fin comme dans le détail d'un examen, calculé à partir du score enregistré. ## Données et stockage

- **Chargement à la demande** (depuis la v1.28.0) : `src/data/questions.json` reste la seule source, mais aucun code de l'appli ne l'importe (seuls les tests, via `src/test/questions.ts`) : `vite-question-packs.ts` en découpe au build **un paquet par titre** (module virtuel `virtual:question-pack/<titre>`, une question de plusieurs titres figure dans chaque paquet), importé dynamiquement par `src/lib/question-packs.ts` (`loadQuestionPack`, cache ; un échec est gardé pour la page (Chromium ne retente jamais un `import()` échoué de la même URL) et « Réessayer » recharge la page (`window.location.reload()`) ; `public/_redirects` répond une vraie 404 pour un fichier de `/assets/` disparu après un déploiement ; `preloadQuestionPack` au repos, lancé par l'accueil seulement quand un titre est choisi). Hook `useQuestionPack` (`src/lib/use-question-pack.ts`) et état « Chargement des questions… » / échec + « Réessayer » (`QuestionPackStatus`) pour l'examen (nouvel examen seulement : la reprise ne charge rien), la révision et le détail d'un examen (paquet du titre de l'examen). Les nombres de `/titre`, des fiches et de l'en-tête de la révision viennent de `src/lib/title-counts.ts` (191 / 209 / 258 officielles + 100 mises en situation), vérifiés contre les données par `title-counts.test.ts` : **les changer avec les données**. `questionsForTitle(title, pool)` et `buildExam(pool)` prennent le paquet en argument. Le setup de test (`src/test/setup.ts`) met les trois paquets en mémoire avant chaque test.
- `src/data/questions.json` : 625 questions. IDs **1–191 = liste officielle CSP** (carte pluriannuelle), **192–291 = mises en situation**, **292+ = questions d'une autre liste officielle seulement** (carte de résident 292–467, naturalisation 468–625 depuis la v1.20.5). Le filtre « Sans les mises en situation » se fait sur `notion !== 'mise-en-situation'` (depuis la v1.13.0) ; seule `notion` dit si une question est une mise en situation.
  ```json
  {
    "id": 1,
    "theme": "Principes et valeurs de la République",
    "notion": "devise-symboles",
    "lists": ["pluriannuelle", "resident"],
    "crNumber": 19,
    "question": "…",
    "answers": ["…"],
    "distractors": ["…", "…", "…", "…"],
    "explanation": "…",
    "group": "fete-nationale",
    "source": { "url": "https://…", "label": "…" }
  }
  ```
  - `answers` : une ou plusieurs bonnes réponses ; l'examen en tire une au hasard, la révision et le détail affichent `answers[0]`.
  - `distractors` : souvent plus de 3 ; l'examen en tire 3 au hasard.
  - `group` (facultatif) : deux questions du même groupe ne tombent jamais dans le même examen.
  - `notion` (obligatoire) : sous-thème officiel, de la liste fermée `NOTIONS` de `src/lib/exam.ts` ; `mise-en-situation` pour les IDs 192–291 et jamais ailleurs ; une notion classique n'appartient qu'à un thème. Classement 1–191 fait sur le fond (la liste officielle ne publie pas les sous-thèmes) ; vérifié par `src/data/notions.test.ts`, qui contrôle aussi qu'il y a assez de groupes distincts pour chaque case de `EXAM_BLUEPRINT`.

(facultatifs, repère de position : id de la première carte sous la bande collée et sa distance sous la bande ; la révision revient sur cette carte si elle est encore listée, sinon sur `scrollY`, car les cartes révélées ou masquées n'ont pas la même hauteur) }`, valeur illisible = ignorée, « À revoir » sans question ou thème inconnu = « Tous les thèmes », « Cet examen » jamais mémorisé) ; `theme` (`light` | `dark`), `motion` (animations, `on` | `off` ; lu et écrit uniquement par `src/lib/motion.ts`, valeur absente ou illisible = pas de choix : défaut `off` si `prefers-reduced-motion: reduce`, sinon `on` ; appliqué par l'attribut `data-motion` de la racine, posé aussi par `public/theme-init.js` avant le premier rendu), `target-title` (titre visé, chaîne brute : `pluriannuelle`, `resident` (depuis la v1.14.0) ou `naturalisation` (depuis la v1.21.0) ; lu et écrit uniquement par `src/lib/target-title.ts`, toute valeur inconnue ou illisible = pas de choix). Sans `target-title`, l'accueil renvoie vers l'écran du titre (`/titre`, sans état de navigation : `TitreVise` décide seul de la page de première visite, par la règle « aucun titre, aucun historique, aucun examen en cours »), sauf si un historique ou un examen en cours existe : la carte pluriannuelle est alors considérée comme choisie, sans rien écrire. Les examens stockés (`ExamRecord` de `quiz-history`, `ExamInProgress` de `exam-in-progress`) portent depuis la v1.13.0 un champ facultatif `title` (clé de titre) ; une entrée sans `title` ou avec un titre inconnu compte pour `pluriannuelle` (`titleOf`), sans jamais être réécrite. Le compteur « n sur 3 », les « Derniers examens », les questions « À revoir » et la reprise ne prennent que les examens du titre choisi (`loadHistoryForTitle`, `loadProgressForTitle`) ; un examen en cours d'un autre titre n'est pas proposé (ni effacé). La pluriannuelle garde la clé `exam-in-progress` telle quelle (progression sans `title` ou de titre inconnu comprise : rien d'existant n'est déplacé ni réécrit), la carte de résident a la sienne ; une progression n'est jamais lue pour un autre titre que celui de sa clé, et démarrer, terminer ou supprimer l'examen d'un titre ne touche pas celui de l'autre (`saveProgress`, `clearProgress(title)`, `loadProgressForTitle`, `hasProgress` de `src/lib/exam-types.ts`). Types et accès à la progression dans `src/lib/exam-types.ts` ; l'historique est lu et écrit uniquement par `src/lib/history.ts` (lecture tolérante : données illisibles ou entrées incomplètes ignorées ; les anciens examens sans `id` ni `answers` restent listés à l'accueil, sans lien vers le détail). `AnswerRecord` porte depuis la v1.22.1 un champ facultatif `answer` : la bonne réponse proposée à l'examen (`ExamQuestion.answer`), écrite pour chaque réponse validée et pour les questions sans réponse du chrono expiré ; absent des examens et progressions d'avant (jamais réécrits), ignoré à la lecture s'il n'est pas une chaîne (`findExamRecord`). Le détail d'un examen l'affiche s'il fait encore partie des `answers` de la question ; sinon une seule bonne réponse = inchangé, plusieurs = « Bonnes réponses acceptées » (toutes, séparées par des virgules). Changer la forme d'une de ces clés = penser aux données déjà stockées chez les utilisateurs.

## Board Trello « Test Civique »

Board : https://trello.com/b/p0hDnJZX (créé le 2026-11-20). Les identifiants vivent dans `.env` (jamais dans ce fichier) : `TRELLO_API_KEY`, `TRELLO_TOKEN`, `TRELLO_BOARD_ID`, `TRELLO_LIST_BACKLOG`, `TRELLO_LIST_TODO`, `TRELLO_LIST_DOING`, `TRELLO_LIST_REVIEW`, `TRELLO_LIST_DONE` (modèle : `.env.example`).

- **Backlog** : idées non cadrées (l'utilisateur y note ses demandes hors session)
- **Todo** : cartes ordonnées par priorité ; étiquette verte « cadré » = ticket dev rédigé. Être en Todo n'autorise pas le démarrage : le go explicite de l'utilisateur reste requis
- **En cours** : une carte = un sous-agent = une PR en draft (commentaire « Dev en cours — sous-agent du TL, branche, PR #n »)
- **En review / test** : PR ready, revue du TL puis test par l'utilisateur
- **Done** : mergé, avec l'entrée correspondante dans `docs/journal-avancement.md`
- Toute carte déplacée ou créée va en haut de sa liste (`pos=top`) ; le TL annonce en une ligne toute carte qu'il crée d'office
- Listes « Batch — … » et « Pr <n> » : voir `docs/workflow.md`, sections 3 et 9 ; étiquette bleue « action admin » = tâche de l'utilisateur, ignorée au cadrage

Lecture d'une liste (jamais « Done » en scan de routine, `desc` seulement sur une carte précise) :
```
set -a; . ./.env; set +a
curl -s "https://api.trello.com/1/lists/${TRELLO_LIST_TODO}/cards?fields=name,shortUrl,labels&key=${TRELLO_API_KEY}&token=${TRELLO_TOKEN}"
```
Lecture des 4 listes de routine d'un coup (début de session, `/start`). Le shell de la machine est **zsh** : pas de syntaxe propre à bash comme `${!var}` ; cette boucle marche sous zsh comme sous bash :
```
set -a; . ./.env; set +a
for pair in "Backlog:$TRELLO_LIST_BACKLOG" "Todo:$TRELLO_LIST_TODO" "En cours:$TRELLO_LIST_DOING" "En review / test:$TRELLO_LIST_REVIEW"; do
  echo "== ${pair%%:*}"
  curl -s "https://api.trello.com/1/lists/${pair##*:}/cards?fields=name,dateLastActivity,labels&key=${TRELLO_API_KEY}&token=${TRELLO_TOKEN}" \
    | python3 -c "import sys,json;[print('-',c['name'],'|',c['dateLastActivity'][:10],'|',','.join(l['name'] for l in c['labels'])) for c in json.load(sys.stdin)]"
done
```
Déplacer une carte : `curl -s -X PUT "https://api.trello.com/1/cards/<CARD_ID>?idList=<LIST_ID>&pos=top&key=${TRELLO_API_KEY}&token=${TRELLO_TOKEN}"`
